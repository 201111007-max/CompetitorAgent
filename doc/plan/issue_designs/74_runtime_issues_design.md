## 0. 设计依据：为什么需要一份「运行时诊断」设计

此前文档（doc 73）记录的是**产物质量**缺陷；本次通过逐行审计 2026-08-30 13:20-13:26 窗口的会话日志
（`~/.competitor_agent/logs/sess_*.log`），发现**运行期缺陷**——同一窗口内两类会话用了**两个不同 LLM
端点**、子 Agent 存在**瞬时完成/空结果被当成功**、外部通道**单点拖垮整维**、Lead **无限循环重试**。
这些是影响每次运行质量/成本的根因级问题，需要专门的修复方案存档。

**已核实事实（不臆测，均读日志）**：

| 会话 | 时间 | model / base_url | elapsed | 特征 |
|---|---|---|---|---|
| `sess_1788096009768`（市场普查） | 13:20-13:26 | `deepseek-v4-flash` @ `ark.cn-beijing.volces.com` | 5~7s（正常） | 20 次 llm.call，产出丰富报告 |
| `sess_13e521ab` 等 ~15 个「只有 codex 的功能」 | 13:23-13:24 | **`deepseek-chat` @ `https://api.deepseek.com`** | **0ms** | 瞬时完成；feature 子 Agent 仅 1 次 1398+57 tokens 即收尾（退化结果） |

代码事实：`LLMClient` 由 `facade/api.py` 装配（`self._llm or LLMClient(...)`）；`DelegateRunner._run`
（delegate_tool.py:131）任何 `runtime.run()` 返回都置 `status="done"`；`_collect_candidate` 不校验
REPORT_SCHEMA 结构；Lead 循环 `max_steps=None`（api.py:1044）无步数上限。

## 1. 问题现状

### 1.1 【P0】运行时 LLM 端点/Key 不一致（env 污染）

- **现象**：同一窗口内部分会话用 `deepseek-chat` @ `api.deepseek.com`（elapsed 0ms、退化输出），其余用
  正确 ark `deepseek-v4-flash`。
- **成因**：opencode shell 的 `DEEPSEEK_API_KEY`（sk-d69…，DeepSeek 格式）遮蔽用户级注册表
  `HKCU:\Environment` 的 Ark key（ark-cde2…）；相关进程继承 shell env 构造了错误端点的 LLM 客户端。
- **影响**：空/超快返回未被识别为异常；报告质量/成本不可预期；同一套代码不同入口行为不一致。

### 1.2 【P0】子 Agent 结果无「最小成功校验」

- **现象**：`DelegateRunner._run`（delegate_tool.py:131）任何返回都置 `done`；`_collect_candidate` 不校验
  REPORT_SCHEMA；57-token 空分析也被当作已收集。
- **成因**：只按「进程没抛异常」判成功，没按「产出有效结果」判成功。
- **影响**：瞬时/空结果污染候选收集器 → 空矩阵、低置信、误导提示（与 doc 73 问题 1.3/1.4 叠加）。

### 1.3 【P1】报告正文质量（重复/截断围栏/提示抄写/守卫被绕过）

见 **doc 73 §1.1-1.3**，本 doc 不重复；修复方案见 doc 73 §3.1-3.3。

### 1.4 【P1】普查 vs 对比：空矩阵 + 误导提示 + compare.json 空壳

见 **doc 73 §1.4** 与 §3.4；本 doc 补充其与 §1.2 的叠加效应（子 Agent 结果校验失效会放大空矩阵）。

### 1.5 【P1/P2】外部通道脆弱，单点拖垮整维

- **现象**：搜索用量超限、Windsurf/OpenAI 官网反爬反复失败、SWE-bench/Terminal-Bench/Aider 榜单接口
  404、HN/Reddit SSL 失败 → performance 维度完全无数据（conf 0.2）。
- **成因**：每维度单一主通道，无维度级兜底；重试无熔断/退避上限。
- **影响**：数据缺口 + Lead 大量轮次干烧（见 §1.6）。

### 1.6 【P2】Lead `max_steps=None` 无限循环 + 成本/轮次无上限

- **现象**：日志显示 Lead 大量轮次都在重试同一失败源（Windsurf/OpenAI 反爬）。
- **成因**：`_react_loop`（api.py:1044）`max_steps=None`，靠 LLM 自然收敛，无软上限/无进展检测。
- **影响**：成本不可控、响应变慢；失败源占用编排轮次挤占有效采集。

## 2. 总体架构：运行时健壮性四道防线

```
运行时防线（本 doc）          产物质量防线（doc 73，已另立）
┌─────────────────────┐     ┌──────────────────────────┐
│ ① 配置自检（§3.1）     │     │ 报告正文净化/去重/守卫布尔化  │
│ ② 结果校验 gate（§3.2）│     │ 普查 vs 对比渲染/导出决策     │
│ ③ 通道熔断+兜底（§3.5）│     └──────────────────────────┘
│ ④ 编排步数/预算（§3.6）│
└─────────────────────┘
 均为确定性/配置化，正常路径零改动（黄金回归安全）
```

**原则**：①④ 是**装配/配置层**改动，②③ 是**执行层**改动，全部只在「异常形态」触发；正常单竞品分析
路径逐字节不变（doc 70/72 黄金回归纪律延续）。

## 3. 接口设计（每项多个修复思路，按可落地性排序）

### 3.1 【P0】LLM 端点自检（防 env 污染）

| # | 思路 | 说明 |
|---|---|---|
| 1 | **构造时端点校验** | `LLMClient.__init__` 校验 `base_url+model` 与 `review_config.yaml` 声明一致，不一致打 WARNING 或拒绝启动（配置漂移检测，Kubernetes ConfigMap 校验思路） |
| 2 | **启动脚本显式注入 + 打印端点** | webapp/CLI 启动从 `HKCU:\Environment` 读用户级 env，不继承 shell 临时 env；启动日志打印「LLM 端点 = …」（12-factor 配置显式化） |
| 3 | **端点白名单** | `base_url` 只允许配置合法值，非法值抛错而非静默用错端点（allowlist 配置） |
| 4 | **异常快照告警** | llm.call 事件已带 base_url/elapsed/completion_tokens → `elapsed<阈值 && completion==0` 记 error 级进 trace（Langfuse/LangSmith 异常 trace 检测） |

### 3.2 【P0】子 Agent 结果「最小成功校验」

| # | 思路 | 说明 |
|---|---|---|
| 1 | **语义 gate** | `_collect_candidate` 前校验 `json.loads` 出 `competitor + dimensions[]`，不合法标 `error` 不收集（复用 `_parse_report`/`aggregate_payload_valid`）——meaningful-output gate（Anthropic/OpenAI agent SDK 的 final-answer 校验） |
| 2 | **空结果重试一次** | 空/畸形 → 回灌「结果为空/格式错，请基于工具输出重答」重跑 1 次（self-correction loop，限次控成本） |
| 3 | **最小 LLM 调用门禁** | subagent span 内 `llm.call` 计数 0 或耗时 <200ms → 判异常路径 |
| 4 | **失败语义四态收敛** | `DelegateRunner` 区分 `done/error/empty/timed_out`，`empty` 不冒泡为成功，`await_terminal` 后明确提示 |

### 3.3 【P1】报告正文质量 —— 见 doc 73 §3.1-3.3（不重复）

### 3.4 【P1】普查 vs 对比 —— 见 doc 73 §3.4（不重复；本 doc 仅提示与 §3.2 叠加）

### 3.5 【P1/P2】通道熔断 + 维度级兜底

| # | 思路 | 说明 |
|---|---|---|
| 1 | **熔断 + 指数退避 + jitter** | 同一源连续失败 N 次 → 熔断 T 秒并切备用源（circuit breaker + exponential backoff）；现有 Tavily↔DDG、fetch 三级降级扩展到**维度级** |
| 2 | **多源冗余 + 结构化源优先** | pricing 走官方定价/llms.txt 预缓存；performance 扩更多榜单直连（已有 benchmark_scores）；沿用 `SearchProvider`/`SentimentProvider` 抽象做故障转移 |
| 3 | **stale-while-revalidate 缓存** | fetch_cache（24h/7d）→ 反爬站回旧缓存 + 标 as_of 低置信（SWR 策略，报告已做「待核验」标注） |
| 4 | **知识库预取** | 已知反爬站点（Windsurf docs 等）离线预爬进 RAG，运行时走 kb_recall 绕开反爬 |
| 5 | **单源重试预算** | 单源限重试次数（如 2 次），超限转备用并记待核验（timebox per source） |

### 3.6 【P2】编排步数/预算上限

| # | 思路 | 说明 |
|---|---|---|
| 1 | **软上限 + 硬上限** | `lead.max_orchestration_steps`（如 40），超限强制收尾返回 partial（Agent SDK max turns / LangGraph recursion_limit） |
| 2 | **无进展检测** | 连续 N 轮相同工具/无新 URL/信息量不增 → 触发收尾提示或强制聚合（stagnation detection） |
| 3 | **成本护栏挂钩** | 步数与既有 `budget` 联动，超预算提前收尾（budget manager；doc 39 成本控制暂缓，本项只做步数软上限，不冲突） |
| 4 | **收敛提示词** | system/Agent.md 明确「完成关键维度即可收尾，避免同一通道反复重试」（prompt 级成本引导） |

| # | 风险 | 兜底 |

## 8. 核心技术点总结

- **运行期根因**：LLM 端点/Key 被 shell env 污染（同一窗口两套端点、0ms 空返回）+ 子 Agent 无最小成功
  校验（空/退化结果被当成功）——二者是本轮诊断新增的 **P0**，直接决定每次运行质量/成本。
- **四道运行时防线**：配置自检（漂移检测）→ 结果校验 gate（meaningful-output / self-correct / 四态收敛）
  → 通道熔断+SWR 缓存+预取兜底 → 编排步数/预算软上限。
- **产物质量防线**（doc 73）：正文净化/去重/守卫布尔化 + 普查 vs 对比渲染/导出决策，与本 doc 正交可分批落地。
- **业界对齐**：配置漂移检测、异常 trace 检测（Langfuse/LangSmith）、meaningful-output gate、circuit
  breaker + exponential backoff、stale-while-revalidate、Agent SDK max-turns/budget manager——均映射到具体代码落点。
- **状态**：2026-08-30 用户决定**暂不修复，仅记录存档**；实施优先级 P0 > P1 > P2。

## 9. 面试演示支撑：叙事 vs 系统能力缺口（2026-08-30 追加，与 doc 73/74 依赖排序）

可复现性）是最后一块拼图；而 doc 73/74 的 P0 修复是这块拼图可信的前提。
